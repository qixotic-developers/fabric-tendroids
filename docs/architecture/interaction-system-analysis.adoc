== Executive Summary

This document analyzes the current architecture of the creature-tendroid interaction system to identify structural issues causing fragile behavior. The goal is to understand the existing data flow before proposing a cleaner design.

=== Key Findings

1. **Multiple disconnected movement paths** - Keyboard and test animation move creatures through completely different code paths
2. **Contact detection uses static geometry** - Tendroid surface position doesn't account for deflection or wave motion
3. **Scattered state management** - Position, deflection, contact, and color states managed by different controllers with no single source of truth
4. **Redundant distance calculations** - At least 3 separate modules compute creature-tendroid proximity

== Problem Analysis

=== Issue 1: No Single Source of Truth for Tendroid Surface

The actual position of the tendroid surface at a given height depends on:

1. **Base position** - Static, set at spawn
2. **Deflection angle** - Changes per-frame based on creature proximity
3. **Deflection axis** - Direction of bend (now latched)
4. **Wave displacement** - Global sinusoidal motion

Currently, mesh deformation computes this combined transform, but the result is not exposed for collision detection.

=== Issue 3: Contact Detection Path Mismatch

|===
|Keyboard Mode |Test Mode

|`CC.update()` called by animation loop
|`CC.update()` called by animation loop

|Velocity from keyboard → position
|Position teleported → velocity calculated

|`check_tendroid_interactions()` runs
|`check_tendroid_interactions()` runs

|Interactions returned to animation loop
|Interactions returned to animation loop

|Animation loop triggers color effect
|Animation loop triggers color effect
|===

**The paths look similar but:**

- Keyboard: Position changes smoothly, velocity is causal
- Test: Position jumps instantly, velocity is derived (effect not cause)

This means deflection detection (which checks velocity direction) behaves differently.

== Summary of Architectural Issues

1. **No unified geometry model** - Each system computes tendroid position independently
2. **Multiple movement interfaces** - Keyboard and test don't share abstraction
3. **Contact uses wrong geometry** - Static position instead of bent surface
4. **State scattered across controllers** - No single source of truth
5. **Code path divergence** - GPU/CPU/no-bubble paths handle interactions differently
6. **Velocity semantics differ** - Keyboard: cause, Test: effect

== Next Steps

This document maps the current state. The next phase is to design a cleaner architecture with:

1. **Single Tendroid Surface Query** - One function that returns actual surface position accounting for all transforms
2. **Unified Movement Interface** - Both keyboard and test feed into same physics system
3. **Centralized Proximity Calculator** - One module for all distance computations
4. **Response Orchestrator** - Single coordinator for deflection → contact → color → input lock flow

See: `docs/architecture/interaction-system-proposal.adoc` (to be created)
