== Executive Summary

This proposal responds to `interaction-system-analysis.adoc` (the _analysis_). It was written after checking the analysis against the code, and that check changed the problem statement.

The analysis says contact detection runs but uses the wrong (static) geometry. The code shows something more basic: *contact detection, shock, repulsion, input lock and recovery never run at runtime, in any mode.* The pieces exist and are unit-tested, but nothing connects them. Fixing the geometry alone would fix nothing the user can see.

The proposal therefore *wires and unifies what already exists* and adds only the pieces that are genuinely missing:

1. `TendroidSurface` - one pure function that answers "where is the bent, waved tendroid at height Y?" (missing today; the only copy of the formula lives inside the Warp kernel).
2. `InteractionSystem` - one per-frame step, called from every animation path, that turns creature position + tendroid surfaces into contacts.
3. The existing `RecoveryOrchestrator` becomes the response layer (contact -> colour -> velocity fade -> input lock -> recovery). It is already built and tested.
4. A single movement write path: `CreatureController.update` is the only code that writes the creature's position; keyboard and test scripts both become `MovementSource` inputs to it.

No new state machines, event bus or service singletons are proposed.

== Problem Statement

Restated from the verified facts:

. *P1 - Disconnected response chain.* A complete, tested response chain exists (`RecoveryOrchestrator`, colour, velocity fade, input lock) with no producer of contact events.
. *P2 - No surface query.* Nothing computes the creature's distance to the actual (bent, waved) tendroid. The formula is private to a GPU kernel.
. *P3 - Frame order and path divergence.* Deflection reads last frame's creature position; in the GPU path the mesh deforms before the creature moves; the CPU path never deforms; the batch path drops deflection.
. *P4 - Two competing movement writers.* `TestController` and `CreatureController.update` both move the creature each frame, on separate update subscriptions with no defined order.
. *P5 - Duplicated formulas.* Wave offset and tip/surface geometry are re-derived in several modules.
. *P6 - Dead code obscures the live design.* Several modules look like part of the interaction system but are not wired.

== Design Principles

. *Wire before you build.* Prefer connecting existing, tested modules to writing new ones.
. *One owner per fact.* Each piece of state or formula has exactly one home; everything else derives from it.
. *One tick, every path.* Interaction is resolved by one step in a fixed place in the frame, independent of the bubble path.
. *Causality.* Position only changes through velocity. Anything that wants to move the creature supplies intent or impulse, never a position.

=== TendroidSurface (single surface query)

A pure module with no USD or Warp imports:

[source,python]
----
def centerline_point(geom, angle, axis, wave_offset, y) -> Vec3
def closest_point(geom, angle, axis, wave_offset, p, samples=16) -> (Vec3, float)   # point on centerline, height
def surface_hit(geom, angle, axis, wave_offset, p, samples=16) -> SurfaceHit        # distance, contact_point, normal
----

* It reproduces the kernel's centerline: the bend is a rotation by `angle * smoothstep(y / length)` about the latched axis, and the wave adds `wave_offset * smoothstep(y / length)`. The kernel applies bubble radial scaling between the two; that scaling is radial, so it does not move the centerline and is ignored here.
* `surface_hit.distance` is centerline distance minus tendroid radius. Closest point is found by sampling the centerline (16 samples is a starting value, to be tuned) and refining the best segment. Distance is measured in 3D to the sampled curve, which removes the analysis's "3D to base point" problem: a creature near the tip is measured against the tip.
* *Parity test (required):* run `launch_deflection_deform` (Warp runs on CPU) on a small mesh for several angles, axes and wave offsets, and assert the Python centerline matches the mean of the deformed cross-section. This is the guard against the formula drifting from the kernel again.
* A single `wave_offset(wave_state, position)` helper replaces the six copies in Python. Kernels keep their own copy (GPU), covered by the same parity test.

=== InteractionSystem (one resolve step per frame)

`InteractionSystem.resolve(dt)` is called by `V2AnimationController._on_update` in all three paths. For each tendroid it:

. reads the current deflection angle and axis from `DeflectionIntegration` and the current wave offset;
. calls `TendroidSurface.surface_hit` for the creature position;
. if `distance <= creature_radius`, calls `RecoveryOrchestrator.handle_contact(contact_point, surface_normal, creature_pos, repulsion_force)`, where the repulsion force points along the surface normal (away from the _actual_ contact point, not the tendroid centre);
. applies the returned repulsion force through `CreatureController.apply_repulsion_force` (velocity, never position);
. calls `RecoveryOrchestrator.update(creature_pos, dt, surface_pos)` and applies its displacement, then derives the input lock from the orchestrator (`is_input_locked`). The lock is _derived_ each frame; `sync_input_lock` becomes unnecessary.

Deflection _detection_ deliberately keeps using the rest cylinder (`approach_calculators`). Deflection is the tendroid's anticipation of an approach; if its trigger depended on its own output, bending away would change the trigger and cause oscillation. Contact, in contrast, is tested against the bent surface because that is what the user sees.

* `MovementSource` is a two-method protocol (`desired_acceleration(position, velocity, dt)`, `is_active()`). It is not an observer/event interface: `CreatureController.update` pulls from active sources once per frame, so there is exactly one place where time advances.
* `KeyboardSource` wraps the current acceleration code unchanged, including `filter_keyboard_by_lock`.
* `TestController` stops writing `position`/`velocity`. It exposes a `WaypointSource` and keeps its timing and metrics. Its update is called from the same animation frame, so the test and creature can no longer double-move.
* Velocity is now causal in both modes, so deflection detection (which reads velocity direction) behaves identically, and repulsion impulses push a scripted creature off its path as they would a keyboard-driven one. The script re-steers afterwards; tests that assert exact positions need a tolerance, and tracking error becomes a reportable metric.
* The test's `InputLockReason.TEST` lock keeps blocking only the keyboard source.

== Migration Plan

Each step is independently shippable and testable. Run tests with `pnpm nx test qixotic.tendroids`.

. *TendroidSurface and parity test.* Pure module plus the kernel-parity test. No behaviour change. Test it first (TDD): flat case (zero angle, zero wave) equals the cylinder axis; bend and wave cases match the kernel.
. *InteractionSystem, contact detection only, behind a flag.* Called from `_on_update`; logs contacts, changes nothing. Gives the first runtime evidence that contact now fires.
. *Wire `RecoveryOrchestrator` and repulsion.* Orchestrator replaces the dead `ColorEffectController` hookup; input lock derived. This is the first user-visible change.
. *Unify movement.* `MovementSource`; move `TestController` onto `WaypointSource`; remove its direct position writes.
. *Reorder the frame.* Deflection after creature, deform after interaction, same order for all paths; fix the CPU path.
. *Remove duplicates and dead code.* Single `wave_offset()` helper; apply the dead-code decisions below.

== Risks

* *Kernel parity.* The Python surface must keep matching the kernel. The parity test is the control; without it the original duplication returns.
* *Reordering the GPU path.* Moving the creature update ahead of deformation changes when bubble pops and visuals are computed. Needs a check against `_update_gpu_path` (`animation_controller.py:250-327`) during step 5.
* *First real contacts.* Because this code has never run in the scene, thresholds (`shock_impulse` 25, `max_speed` 50, `avoidance_epsilon` 30) and the recovery tuning have never been exercised together. Expect a tuning pass after step 3.
* *Test changes.* Tests that assume the teleport model need tolerance-based assertions.
* *No test coverage today* for `animation_controller`, `creature_update_helpers` or `TestController`; step 2 adds the first.

== Open Questions

. Should the CPU bubble path deform the mesh with deflection? Today it does not, which may be intentional.
. Is the analytic contact query enough, or is PhysX contact reporting (`ContactHandler`) wanted?
. If a tendroid deflects away before the creature touches it, should contact still be possible? The design says yes, because contact is tested against the bent surface; confirm that is the intended behaviour.
. Should the GPU batch deformer gain deflection support, or stay a fast path used only when nothing is deflecting?
. Are `proximity/hash_grid` and the batch detection kernel planned for later use?
